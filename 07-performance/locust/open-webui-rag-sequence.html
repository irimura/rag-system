Plan 1b / Open WebUI / Knowledge RAG

プロンプト送信から回答表示までのRAGシーケンス

Open WebUI v0.9.6、Chroma、BAAI/bge-m3、BAAI/bge-reranker-v2-m3、Node AのvLLMという案1b構成を対象に、補助生成・検索・Batch・最終生成・回答後処理を時系列で示します。

Node B: Open WebUI内蔵RAG Node A: vLLM Hybrid: BM25 + Vector + Rerank
CONTENTS 1. 処理の区分 2. 全体シーケンス 3. 並列検索 4. 計測ポイント 5. Batchログ 6. 解釈上の注意

1. 処理は3区間に分かれる

PRE-RETRIEVAL

受付・検索クエリ準備

認証、モデル設定、Knowledge参照情報を解決し、設定に応じてvLLMで検索クエリを生成します。

RETRIEVAL

検索・統合・rerank

Chroma全件取得、BM25、query embedding、vector検索、RRF統合、CrossEncoder rerankを行います。

GENERATION

回答生成・表示

取得チャンクをプロンプトへ挿入し、vLLMの生成結果をSSEで表示します。終了後に補助タスクが走る場合があります。

3. 複数のBatchesが見える理由

Open WebUI v0.9.6は、取得済みのKnowledgeコレクションと検索クエリを組み合わせ、collection数 × query数 の検索タスクを作ります。各タスクがquery embeddingとrerankを呼ぶため、ログには複数のBatchが並行して現れます。

flowchart LR
    S["検索開始"] --> T1["Collection A × Query 1"]
    S --> T2["Collection A × Query 2"]
    S --> T3["Collection B × Query 1"]
    S --> T4["Collection B × Query 2"]
    T1 --> E1["Embedding Batch"] --> R1["Rerank Batch"]
    T2 --> E2["Embedding Batch"] --> R2["Rerank Batch"]
    T3 --> E3["Embedding Batch"] --> R3["Rerank Batch"]
    T4 --> E4["Embedding Batch"] --> R4["Rerank Batch"]
    R1 --> M["結果を統合"]
    R2 --> M
    R3 --> M
    R4 --> M

例: 2 collection × 2 queryなら検索タスクは4件です。各タスクでembeddingとrerankが1回ずつ呼ばれる場合、最大8個のBatch呼び出しが混在します。

4. 性能計測で分離したいステージ

順序ステージ主な資源測定範囲体感遅延への影響

2collection_fetchChroma I/O全チャンク・metadataの取得コーパス量とcollection数に依存
3bm25_build_searchNode B CPUBM25構築から上位k件取得全チャンクを対象に毎回構築するコスト
4query_embeddingEmbedding Batchbge-m3のencode呼び出しquery数×collection数に応じて増える

6rrf_mergeNode B CPUBM25・vector結果の統合と重複排除候補件数が小さければ通常は軽い
7rerankRerank BatchCrossEncoderのpredict呼び出し候補ペア数とCPU性能に依存
8rag_prompt_buildNode B CPUチャンク・引用のプロンプト挿入コンテキスト量が大きいと後段prefillにも影響
9vllm_ttftNode A GPU最終生成要求から最初の回答チャンクモデル待ち、転送、prefillを含む
10stream_totalNode A GPU最初の回答チャンクから生成完了出力長とdecode速度に依存

5. Batch識別ログとの対応

RAG_BATCH_START id=emb-0123456789ab type=embedding items=1 batch_size=1 batches=1
RAG_BATCH_END   id=emb-0123456789ab type=embedding status=success elapsed_ms=234.1

RAG_BATCH_START id=rerank-abcdef012345 type=rerank items=9 batch_size=32 batches=1
RAG_BATCH_END   id=rerank-abcdef012345 type=rerank status=success elapsed_ms=918.6

同じidのSTARTとENDを対応付けます。itemsはモデルへ渡した入力数、batchesは設定バッチサイズから算出した内部Batch予定数です。

6. 解釈上の注意

  • 検索クエリ生成、タイトル、タグ、フォローアップは設定や会話状態により実行されない場合があります。
  • hybrid searchに失敗すると通常のvector searchへフォールバックするため、実ログではシーケンスが短くなる場合があります。
  • Sentence TransformersのBatchesはNode Bのembedding／rerank進捗であり、vLLMのcontinuous batchingとは別物です。
  • 回答後の補助生成は初回回答表示後に続くことがあり、ユーザー体感の回答時間とログ終端時刻が一致しない場合があります。
  • この図は案1bを対象とし、案2・案3の外部RAG API経路にはそのまま適用しません。
