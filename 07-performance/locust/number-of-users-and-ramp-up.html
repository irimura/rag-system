Locust performance testing guide

Number of Users と Ramp up の理解

仮想ユーザーを何人動かし、どの速さで起動するか。レスポンス約10秒のチャットシステムを例に、負荷の立ち上がりと処理中ユーザー数を時間軸で理解します。

GUIDE 基本用語 数値例 タイムチャート wait_time 処理中ユーザー 典型パターン 試験計画

01 / DEFINITIONS

まず、2つの役割を分ける

U

Number of Users

Locustが同時に動作させる仮想ユーザーの目標数です。起動済みユーザーには、レスポンス待機中とwait_time中の両方が含まれます。RPSや同時処理数そのものではありません。

R

Ramp up

目標ユーザー数まで増やす速度（users started/second）です。最大人数ではなく、そこへ到達する過程を制御します。値が大きいほど一斉アクセスに近づきます。

基本関係 目標到達時間 ≈ Number of Users ÷ Ramp up 実際には最初のユーザーが直ちに起動するため、最後のユーザーの起動時刻は概ね (Users − 1) ÷ Ramp up です。

04 / WAIT TIME

Ramp upとwait_timeは別の時間軸

Ramp up

テスト開始時に新しい仮想ユーザーを追加する速度。目標人数へ到達すると役割を終えます。

Response time

各ユーザーが質問を送り、回答を受信し終えるまでの時間。この間、そのユーザーは処理中です。

wait_time

回答完了後、次の質問まで各ユーザーが待つ時間。起動済みの間、タスクごとに繰り返し適用されます。

飽和前の概算（1タスク＝HTTP 1件） RPS ≈ Users ÷（平均Response time + 平均wait_time） 処理中の時間割合 ≈ Response time ÷（Response time + wait_time）
条件（10 Users）平均Response平均wait概算RPS処理中割合
限界試験10秒0秒約1.00ほぼ100%
現在の簡易試験10秒2秒約0.83約83%
利用者思考時間あり10秒20秒約0.33約33%

05 / IN-FLIGHT REQUESTS

Number of Usersは「処理中ユーザー数」ではない

Locust標準のNumber of Usersグラフは、起動している仮想ユーザー総数を表示します。レスポンス待機中とwait_time中を区別しません。

時間平均を推定する

平均処理中リクエスト数 ≈ POST RPS × 平均応答秒
Littleの法則による概算です。POST行のRPSを使い、独自SSEイベント込みのAggregated RPSは使いません。

瞬間値を測定する

リクエスト開始時にin-flightを+1、終了時に−1する独自ゲージが必要です。標準HTMLレポートには直接表示されないため、ログ、CSV、Prometheus等へ出力します。

wait_time=0の場合: 同期的に1ユーザー1リクエストを送る現在のシナリオでは、定常時のNumber of Usersと処理中ユーザー数はほぼ一致します。wait_timeがある場合は一致しません。

06 / BEHAVIOR PATTERNS

並列度を増やしたときの典型パターン

余力あり

Users↑ → POST RPS↑

p50・p95がほぼ一定、失敗率0%。Users増加に処理量が比例します。

待ち行列化

RPS横ばい → TTFT↑

Usersを増やしてもRPSが伸びず、回答開始前の待ちが増えます。

生成速度低下

TPOT↑ → tokens/s↓

同時生成負荷により、個々のストリームの生成速度も低下します。

容量超過

p95↑ → Failures/s↑

タイムアウトやHTTPエラーが増加。持続可能な許容範囲を超えています。

UsersPOST RPSp95失敗率読み方
