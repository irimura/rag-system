Cerebrasはいかにしてエンタープライズナレッジベースを構築したか

Isaac TaiDaniel KimMike Gao

従業員は社内ナレッジベースへ毎日15,000件以上の質問をしています。公開から3か月で、社内で最も広く使われるツールの一つになりました。人だけでなく、自動処理やエージェントも利用しています。

Cerebrasのチームは、データセンター運用、チップ設計、ハードウェア、学習、推論、クラウドプラットフォームなど、幅広い領域を担当しています。毎年数百人が入社するなか、社内のコミュニケーションチャンネルには同じ質問が繰り返し投稿されていました。

「Xはどこにありますか？」
「Yの専門家は誰ですか？」
「Zとは何ですか？」

そこで、人やシステムを必要な情報へ結び付けるためにCerebras Knowledgeを構築しました。

既存のデータ保管先を生かす

組織内で情報を見つけるのは困難です。データは複数のツールに散在しています。そのため、すべてを一つのプラットフォームへ記録し、情報を一か所に集めようという案が繰り返し提案されます。しかし、単一の情報源へ統合する構想が実際に機能することは、ほとんどありません。

情報は、その作業に適した場所で生まれます。文書の修正提案、Slackのスレッド、GitHubのコード参照、Jiraのステータス情報などです。各プラットフォームは特定の用途に合わせて設計され、長年の製品開発と分析によって最適化されています。たとえば、Google Docsでプルリクエストを議論するのは非効率です。

そこで、既存の業務手順をほとんど変えずに使えるシステムを設計しました。データ収集では、各プラットフォームから直接データを抽出します。

ナレッジベースの構造

このナレッジベースは、次の三つの機能を提供します。

  1. 社内データの収集と保存
  2. 収集したデータの検索
  3. 監査・分析を備えた認証と認可

中核となるのは、複数のソースから得た埋め込み、要約、メタデータを保持する単一のPostgresテーブルです。システムは社内全体から継続的にデータを取り込み、いつでも検索できる状態を保ちます。

私たちは、単純でありながら多様なデータ形式を扱えるインターフェースを求めていました。また、Cerebrasの開発者が独自のコネクターを追加できることも要件でした。その結果、Slackスレッドからネットリストまで、すべてのソースを同じ埋め込みテーブルへ格納する設計になりました。テーブル内のデータは、同じインターフェースからすぐに検索できます。

各データソースでは、データの内容、接続方法、取得頻度を定義します。生成される埋め込み行は、Slack、コードリポジトリ、文書システム、カスタムデータベースのいずれに由来しても、同じインターフェースに従います。

Slack

Slackは、設計上最も重要なデータソースでした。社内で最新の技術的な議論が行われる場所だからです。

非構造化されたSlack会話の処理

当初は、未加工テキストを単純に埋め込むだけで十分な性能が得られるか試しました。しかし、関連データを漏れなく検索するには、ベクトル検索だけでは不十分だと分かりました。

Slackメッセージには、次の課題があります。

  • 情報密度が大きく異なります。「ああ、いいよ、マイク」という発言も、カーネルの詳しい説明も、同じ1件のメッセージです。
  • メッセージの長さはさまざまです。コサイン類似度では、短いメッセージが長く詳しいメッセージを上回ることがあります。
  • メッセージの意味は、前後の会話に依存することがあります。

そこで、複数の検索手法を組み合わせました。すべてのSlackスレッドを複数の方法で同時に検索し、各手法がほかの手法の弱点を補います。

  • 全文検索は、エラー文字列、フラグ名、ホスト名など、完全一致が重要なトークンを捉えます。エンジニアがエラーメッセージをそのまま貼り付けた場合は、字句の完全一致が最も有力な根拠になります。
  • 埋め込み検索は言い換えを捉えます。「マニフェストの読み込み後にリストアが停止する」という質問と、「NFSマウントでチェックポイントが止まる」という回答には共通語がないかもしれません。ベクトル類似度は、異なる言葉で書かれた質問と回答を結び付けます。1
  • 逆文書頻度（IDF）は、有用な情報と価値の低い発言を区別します。珍しい設定フラグなど、希少なトークンを含む短いメッセージは上位に置く価値があります。一方、「よさそう、ありがとう！」のような発言は、多くのクエリと意味的に近くても、語の希少性を考慮するとスコアがほぼゼロになります。
  • 経過時間による減衰は、Slackの回答が古くなることを考慮します。同じ質問に答える二つのスレッドがあっても、6か月前の回答は、すでに廃止されたインフラを説明しているかもしれません。関連性が同じなら、新しいスレッドを優先します。

Socket Mode

リアルタイムでデータを収集するため、ワークスペースへSlack Botをインストールし、Socket Modeで動作させました。Slackは永続的なWebSocketを通じてメッセージイベントを送信します。そのため、Web APIをポーリングして利用上限を圧迫せずに、更新をリアルタイムで取得できます。

イベントを受信すると、すぐに受領を通知します。イベントIDで重複を排除し、取り込み処理の対象としてメッセージを登録します。

取り込み処理は、新しいメッセージだけを保存するわけではありません。メッセージが属するスレッドを特定し、親メッセージとすべての返信をSlack APIから再取得します。その後、スレッド全体を1行として書き戻します。既存スレッドへ返信が追加されるたびに会話全体を取得するため、保存内容、参加者一覧、最終更新日時は常に最新のスレッドを反映します。

システムでは、Slackチャンネルごとにデータソースを用意しています。これにより、データの更新頻度を細かく調整できます。たとえば、投稿の多いインシデントチャンネルは、ほかのチャンネルより頻繁に取り込めます。

未加工コンテンツにはPostgresの全文検索用GINインデックスを作成しています。そのため、Slackの生テキストは取り込まれた直後からキーワード検索できます。実用的なベクトル検索には、さらに処理を加えます。8

バースト

この段階でSlack検索の精度は上がりましたが、長いスレッド内の重要なメッセージがスレッド単位の要約へ反映されないことがありました。

個々のメッセージを検索しやすくするため、「バースト」を使います。バーストとは、同じ投稿者による連続したメッセージ群です。スレッドのトピックを文脈として先頭へ付け、バーストごとに埋め込みます。2 回答が本筋から外れた1件のメッセージにあり、その語彙がスレッド要約へ含まれない場合でも、バースト埋め込みがあればそのメッセージを単独で検索できます。

有用性の低いデータを除外するため、複数の評価項目を重み付けして各バーストを採点します。次の条件を基に算出したスコアが、しきい値を超えたバーストだけを埋め込みます。

  • コーパス全体で比較的希少な、IDF 4.0以上のトークンを含む
  • 結合後のバーストが200文字以上である
  • バースト内の1件以上のメッセージにリアクションがある

蒸留後、条件を満たすバーストを埋め込み、スレッド単位のレコードとともに埋め込みテーブルへ保存します。

コードリポジトリ

当初は、コードリポジトリを埋め込む必要があるか議論しました。Claude Codeなどのコマンドラインツールが普及し、「grepだけで十分」と思えるなか、コードの埋め込みを作る必要性は明らかではありませんでした。しかし、業界関係者との議論と、大規模コードベースの意味検索に関するCursorの知見を踏まえ、試すことにしました。

社内には多数のリポジトリがあり、40GBを超えるものもあります。主な課題は、埋め込みを効率よく最新の状態に保つことでした。

CocoIndexによるコード埋め込みの更新

いくつかの実験を経て、コードベースのベクトル化に特化したオープンソースの文書埋め込みフレームワーク、CocoIndexを採用しました。

各リポジトリでは、言語固有の正規表現による境界を、粗いものから細かいものの順に使ってコードを分割します。まずクラスなどの上位レベルの境界を試し、チャンクがまだ大きすぎる場合は、メソッド境界、さらに小さなブロックへと分割します。生成したチャンクを埋め込み、ベクトルをPostgresへ書き込みます。一つのファイルから、ファイル単位や関数単位など、粒度の異なる複数の埋め込みが生成される場合があります。

CocoIndexは同期用メタデータをPostgresで管理します。コミットのたびにリポジトリ全体を再計算せず、変更されたコードチャンクだけを再度埋め込み、出力します。同期状態と埋め込みストアが同じデータベースにあるため、この方式はCerebrasの構成に適していました。

コードベースが増えたため、各チームが設定ファイルを提出してリポジトリを登録できるようにしました。設定には、ファイルパス単位の許可リストと拒否リストも含まれます。

カスタムデータソース

独自のデータベースをすでに運用しているチームもあります。ナレッジベースへ参加するためだけに、データをSlackや文書システムへ移すことは望んでいませんでした。既存のテーブルを同じ方法で検索できる仕組みが必要でした。

そこで、カスタムソースをプラグインスクリプトとして扱います。各チームは、自分たちのシステムからデータを読み取り、埋め込みテーブルと同じ形式の行を出力する小さなPythonモジュールと、対応するデータソース設定をプルリクエストで提出します。

スクリプトが共通スキーマで共有データベースへ書き込めば、残りの処理は変更せずに動作します。追加したデータは、Slack、コード、文書と同じ方法で検索でき、ほかの箇所に専用処理は必要ありません。

プランニングとツールの並列実行

クエリを受け取ると、まずLLMが短いプランニング処理を実行し、使用するツールとデータソースを選びます。主なツールは次のとおりです。

  • subsystem_index：ファイルごとのLLM要約
  • search：Slack、Wiki、コード、その他のインデックス済みソースを横断し、内部で統合・再ランキングするベクトル検索
  • search_slack：Slackの直接検索
  • search_code：ソースリポジトリに対するripgrep
  • recent_prs：質問に関連する最近のプルリクエスト
  • who_knows：対象分野の知見を持つ人の検索

プランナーには、インデックス済みデータの概要を渡します。概要には、プロジェクトの一覧、各プロジェクトで利用できるソース、各ソースが回答に適する質問を含めます。プランナーはユーザーのクエリと現在の検索範囲からツールを選びます。実行処理は選ばれたツールを並列に呼び出し、結果を共通の根拠形式へ変換して、回答を生成するLLMへ渡します。4

再ランキング

クエリと語彙が似ているだけで、別の質問に答える文書が上位へ現れる場合があります。そこで再ランキングの前に、各検索器の順位を逆順位統合（Reciprocal Rank Fusion、RRF）でまとめます。文書が現れる一覧ごとに、重み / (60 + 順位)を加算します。既定の重みは1.0、平滑化定数は60です。

平滑化定数を設けると、一つの検索器による高評価より、複数の検索器による一致を重視できます。複数の検索器で上位に現れる文書は、一つの検索器だけで1位になった文書を上回る場合があります。次に、同じソースの重複チャンクをまとめ、各ファイルから採用する件数に上限を設けます。これにより、上位20件の多様性を保ちます。

元のクエリと候補文書を小型の再ランキングモデルへ送り、各文書を0から10で採点します。そのうち上位10件を残します。6

ランキングの確定後、上位文書に周辺情報を追加します。たとえばWikiのセクションが一致した場合は、前後の2セクションも取得します。これにより、チャンク分割で切り離された見出し、前提条件、注意事項を補い、必要な文脈を含む抜粋を提示できます。

検索結果は、複数の検索器から統合し、ソース単位で重複を排除し、実際の質問に対して再ランキングした根拠の集合です。最後に周辺情報を加えてから利用者へ返します。

MCP

MCP統合では、検索機能を一つの回答用エンドポイントへ隠さず、個別のツールとして公開します。クライアントが高速かつ低コストで利用できるように、ツールは単純に保ち、可能な限りLLMを使いません。5

各MCPツールは、search_slack、search_code、search、who_knowsなど、一つの検索機能に対応します。入出力の範囲と形式を明確にし、仕様を安定させています。そのため、ツール内に制御処理を追加しなくても、クライアントやエージェントから容易に呼び出せます。

多くのツールは、ベクトル検索、字句検索、ripgrepなど、一つの検索処理を実行します。軽量な採点規則を適用し、加工前の根拠データを返します。

Claude CodeなどのMCP対応エージェントが、呼び出すツール、実行順序、結果を回答やコード編集へまとめる方法を決めます。検索レイヤーは、リクエストを処理する際にエージェントの判断へ依存しません。

Web UI

Web UIでも同じツールを使いますが、ユーザーの質問ごとに、プランニングから回答生成までの全処理を実行します。UIエージェントがプランナーと実行処理を担当します。

プランナー：軽量なLLM処理がクエリと現在のプロジェクトを調べ、search、search_slack、subsystem_indexなど、呼び出す検索ツールを選びます。

実行処理：選ばれたツールを並列に呼び出して結果を収集し、スコア、更新時期、ソース情報を含む共通の根拠形式へ変換します。

回答生成：最後のLLM処理が、構造化した根拠一式と元の質問を受け取り、引用、注意事項、複数ソースを統合した説明を含む回答を生成します。

利用者はWeb UIへ質問を入力するだけで回答を得られます。内部では、MCPクライアントでも構成できる「プランナー → 実行処理 → 回答生成」の流れを実行しています。

プロジェクトによる情報整理

コーパスが増えると、すべてのデータを常に横断検索する方法は役に立たなくなりました。コンパイラーチームのエンジニアはインフラのRunbookを必要とせず、インフラチームもコンパイラー固有の情報を必要としません。プロジェクトを使い、既定の検索結果を業務に関連する情報へ絞ります。

プロジェクトと検索範囲

クエリの検索範囲を整理するため、プロジェクトを導入しました。プロジェクトは、特定のSlackチャンネル、コードリポジトリ、社内データベース、文書スペースなど、チームや取り組みに関連するデータソースをまとめたものです。

プロジェクトは軽量な参照として実装しています。共有インシデントチャンネルや共通プラットフォームリポジトリなど、同じデータソースを複製せずに複数のプロジェクトから参照できます。

オンボーディングと既定値

オンボーディングでは、ML学習インフラ、コンパイラー、データセンター運用など、担当業務に合う既定のプロジェクトを選択または作成します。

既定のプロジェクトはユーザープロファイルへ保存され、クエリの検索範囲へ自動的に適用されます。新しいエンジニアも、重要なSlackチャンネル、リポジトリ、文書スペースを事前に調べることなく、関連性の高い回答を得られます。

おわりに

このナレッジベースが機能する理由は、情報を一つのシステムへ移すのではなく、既存の保管先から収集する設計にあります。複数の検索手法を組み合わせることで、必要な根拠を素早く提示できます。実際の社内データを扱える柔軟性と、組織の成長後も検索精度を保てる構造を両立しています。
